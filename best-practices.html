Automate meeting notes → action items, end to end

Record, transcribe, summarize and push action items into the tracker automatically — the single biggest unclaimed win in the whole survey.

Impact
Why it matters

Meetings & calls eat 6.8 hrs of a 40-hour week (17%) — and today none of it touches AI. This is the largest untouched block on the schedule.

Recommended workflow
  1. Record with your calling tool's built-in transcript (Teams Premium, etc.)
  2. Drop the transcript into Claude with a fixed prompt: summarize, extract decisions, extract action items with owners
  3. Push the action items straight into Jira / your tracker
  4. Skim once for anything the transcript-bot mis-heard — don't re-read the whole thing
UX example

A design review with PM + 2 devs generates 6 action items across 3 owners. Instead of writing them up after, the summary + tagged owners lands in Jira within 5 minutes of the call ending.

Before → With AI
Before15–20 min per meeting writing up notes, often the next day, often incomplete.
With AISummary and action items ready before you've closed the call window.
Expected benefit

⚡ ~1.4 hrs/week freed, per the report's Lever-1 estimate

Feed the design system before you ask for UI

Before asking AI to design or redesign a screen, hand it the design-system rules, existing patterns and constraints — not just the user goal.

Impact
Why it matters

The single most-repeated cause of wasted time in the whole survey — more than eight people independently named "AI ignored our design system / Lyra standards" as their biggest time-sink, not hallucination or bugs.

Recommended workflow
  1. Before any UI-generation prompt, paste in: the user goal, the business constraint, the relevant design-system components/tokens, and what "out of bounds" looks like
  2. Ask for the component/pattern by name where one already exists — don't let AI invent a new one
  3. Treat the first output as a layout sketch, not a final surface — expect one context-correction pass
UX example

Instead of "design a settings screen with role-based views," specify: "using the Lyra Tabs and Table components, primary/BCP tenant distinction must stay visually explicit per our region-mapping rules, admin/regular-user/guest each map to this permission matrix: [table]."

Before → With AI
Without contextClean-looking flow that ignores tenant/region rules — more time revising than modeling the matrix up front would've taken.
With contextFirst draft respects the constraint; correction pass is cosmetic, not structural.
Expected benefit

✓ Fewer rework cycles, fewer dev pushbacks

Read the raw source before you trust the synthesis

AI finds patterns; you find meaning and catch what it missed. Never let a synthesis go out the door unread against its source.

Impact
Why it matters

One respondent's synthesis missed a subtle but critical pain point that only showed up indirectly across sessions — they'd accepted the AI output without checking, and a stakeholder caught it in the room. Re-doing it cost more time than reading the transcripts up front would have.

Recommended workflow
  1. Let AI produce the first-pass themes, quotes and structure
  2. Read the raw transcripts / notes yourself — in full, not skimmed
  3. Specifically hunt for anything contradictory, emotionally loaded, or mentioned by only one person — these are what AI under-weights
  4. Only then finalize
Before → With AI
Skipping validationFast, but ships a shallow read — the cost surfaces downstream, where it's most expensive to fix.
With validationSame production speed, plus a deliberate re-read pass: "AI drafts, I always read the raw transcripts."
Expected benefit

✓ Avoids costly late-stage corrections

Cross-check one AI tool's output with another

Run the same analysis through two tools and let the disagreement point you at what needs a human decision.

Impact
Why it matters

A single AI output can be confidently wrong. Two independent passes rarely fail in the same place — the gap between them is where your judgment is actually needed.

Recommended workflow
  1. Run research synthesis in Dovetail (or a second tool)
  2. Pass its output to Claude for cross-validation and gap analysis
  3. Wherever the two disagree, that's the item a human reviews — not the items they agree on
UX example

One respondent moved from Dovetail-only synthesis to a Dovetail + Claude pairing specifically because Dovetail alone "did a lousy job" on its own — the second pass caught what the first missed.

Expected benefit

✓ Catches errors neither tool alone would surface

Default to an interactive HTML prototype, not a static Figma flow

For anything time-boxed or behavior-heavy, build a clickable HTML prototype with AI instead of static screens.

Impact
Why it matters

Interactive HTML prototyping is the most-cited "couldn't do this before AI" capability in the entire survey — 15+ of 37 respondents named it unprompted.

Recommended workflow
  1. Define the flow and states in natural language, including edge cases and permission/role variants
  2. Describe components, states and behaviors explicitly (feed the design system first — Practice 02)
  3. Generate the working prototype, then iterate on specific states in follow-up prompts
  4. Share the link directly with PM/dev — no Figma round-trip needed at this stage
Before → With AI
BeforeStatic screens per state, verbal walkthroughs, multiple clarifying rounds before dev understood the behavior.
With AIA full flow with live filters and real-time state changes people could click through and understand immediately.
Expected benefit

⚡ Days → hours · fewer handoff rounds

Hand off a structured .md spec, not just an annotated Figma file

Generate a Markdown spec covering variants, states, interactions and edge cases developers can build from without follow-up questions.

Impact
Why it matters

Development velocity has outpaced design's ability to keep every ticket detailed by hand — a written spec lets developers move independently on standard work.

Recommended workflow
  1. Describe the component/feature to AI in design terms: purpose, variants, states, interactions, content rules, accessibility, edge cases
  2. Generate the .md spec structured for developers, not designers
  3. Review for accuracy — especially edge cases, where AI most often gets it wrong
  4. Share the .md directly; developers work from it independently
Expected benefit

⚡ 2–4× faster · fewer dev round-trips

Post your prompt the same day it saves you real time

The moment a prompt or workflow saves you hours, put it in the shared library — before it becomes "the thing you meant to write down."

Impact
Why it matters

The team is discovering the same fixes independently, over and over. 5 of 17 open comments asked for exactly this, unprompted, in near-identical language.

Recommended workflow
  1. Whenever a prompt/workflow clearly saves time, copy it into the shared library that same day
  2. Tag it by category (see Examples below) and note what it's best for
  3. Let the next person adapt it rather than starting from a blank prompt

↻ Less duplicated discovery, faster ramp-up

Force genuinely divergent directions, not five variations of one idea

Ask explicitly for options that differ in approach, not just styling — don't let AI default to the obvious answer.

Impact
Why it matters

Design ideation is already used AI beyond the team's own self-rated automatable ceiling (−18) — the risk isn't too little AI, it's convergent AI without a forcing function for real divergence.

Recommended workflow
  1. Feed the design brief, user goal and constraint
  2. Explicitly request 5–8 distinct directions, each with its core concept, what makes it different, and its tradeoff
  3. Use the output as a divergence starting point, then generate component variants for the chosen direction
Expected benefit

↑ 2–3× more directions considered

Synthesize every research signal in one sitting, not one source at a time

Pull Confluence, Jira, Dovetail, competitive analysis and customer feedback into one unified pass instead of a week of source-by-source review.

Impact
Why it matters

Decisions used to get made on partial information because full synthesis across every source "rarely happened" in a week — now realistic in a day, so nothing gets deprioritized for lack of time.

Recommended workflow
  1. Export the relevant slice from each source: Confluence, Jira, Dovetail, competitive notes, customer feedback
  2. Feed them into one AI session and ask for a unified view — themes across all sources, not source-by-source summaries
  3. During usability testing, start structuring findings between sessions rather than waiting for the last one to end
Expected benefit

⚡ A week of synthesis → a day

Of six UX phases, Validate is where the team uses AI least — and the one measured gap where "automatable" still outpaces "automated."

Impact
Why it matters

Validate is the phase where the fewest people apply AI significantly — and the only design activity in the automatable-vs-used table with measured room left (+18).

Recommended workflow (to pilot)
  1. Record sessions and get transcripts
  2. Ask AI to tag findings by theme and severity, and produce a ranked list

Examples

Real prompts behind the practices above. Starting points, not scripts — always add your product area, user type and constraints.

Meeting → Action Items, Fully AutomatedAutomation
Here is the transcript of a meeting: [paste transcript]. From it, produce: 1. A 3–5 sentence summary of what was discussed 2. Every decision that was made, listed plainly 3. Every action item, with: what needs to happen, who owns it (use the names in the transcript), and any due date mentioned 4. Open questions that came up but weren't resolved Format the action items so they can be pasted directly into Jira as separate tickets (title + one-line description each).
📍 Operationalizes Practice 01Best for: any recorded meeting, standups, design reviews
Design-System Context BriefPrompting
Before generating any screen or component, here is the context you must respect: User goal: [what the user is trying to accomplish] Business constraint: [key limitation or requirement] Design system: use only [component library name] components — specifically [list relevant components/tokens] Out of bounds: [patterns, colors, or layouts that must NOT be introduced] Accessibility requirements: [ARIA / keyboard / contrast rules that apply] Confirm you understood these constraints before generating anything. If a requirement conflicts with an existing component, flag it — do not silently invent a new one.
📍 Operationalizes Practice 02Best for: any AI-generated wireframe, prototype, or component
Research Synthesis — Multi-Source ThemesResearch
I have [X] sources of user research: [list: interview notes, Jira tickets, Confluence pages, survey data, support tickets]. Analyze all of them and: 1. Identify the top 5 recurring themes across all sources 2. For each theme, provide 2–3 direct evidence quotes 3. Flag any contradictions or gaps between sources 4. Suggest 3 open questions that still need answers Output as a structured document with clear section headers.
📍 Based on Yaara Bar Feldman's workflowBest for: research synthesis, cross-source analysis
Developer Handoff — Component SpecHandoff
Generate a structured developer handoff spec for the following UI component: Component: [name] Purpose: [what it does, user goal] Variants: [list variants] States: [default, hover, active, disabled, loading, error, empty] Interactions: [describe behaviors] Content rules: [character limits, placeholder text, validation rules] Accessibility: [ARIA labels, keyboard behavior, focus order] Edge cases: [what can go wrong, how to handle it] Output as a clean Markdown document (.md) that a developer can work from without needing to ask follow-up questions.
📍 Based on Tali Silon-Shacham's workflowBest for: dev handoff, spec documentation
Design Ideation — Divergent DirectionsIdeation
I'm designing a solution for the following: User goal: [what the user is trying to accomplish] Business constraint: [key limitation or requirement] Context: [product area, user type, platform] Generate 6 distinct design directions. Each should be genuinely different — not just variations of the same approach. For each direction include: - Core concept (1 sentence) - What makes it different - Main tradeoff or risk - What type of user it works best for Do not default to the obvious solution first.
📍 Inspired by Gajanan Rajput's ideation workflowBest for: early exploration, avoiding groupthink
UX Writing — Microcopy for UI StatesUX Writing
Write microcopy for the following UI states: Component: [name] Product tone: [e.g., professional, direct, reassuring] User context: [what the user just did / is trying to do] Write copy for: - Default label / placeholder - Success state - Error state (what went wrong + how to fix it) - Empty state (no data yet) - Loading state Keep it under [X] characters per state. Avoid generic phrases like "Something went wrong." Be specific to what the user is doing.
📍 General — community contributedBest for: microcopy, UI text, all states

✅ Do
⚡Use AI for production work — spec writing, synthesis, annotation, microcopy. The highest-ROI tasks.
📖Always read raw transcripts yourself. AI finds patterns — you find meaning.
✏️Treat AI output as a first draft. 65% need minor edits, 35% need significant rework.
🧩Feed the design system before any UI prompt. The single most-named cause of wasted time.
🔄Use multiple tools to validate each other. Catches errors neither would catch alone.
📤Share what works, the same day. If a prompt saved you 2 hours, add it to Examples.
❌ Don't
🚫Don't use AI output as-is. 0% of the team does — and that's right.
🚫Don't let AI build UI before UX is involved. Creates irreversible design debt.
🚫Don't paste confidential data into public AI tools without checking policy first.
🚫Don't use AI to skip the thinking. Judgment and prioritization stay human.
🚫Don't work in isolation. The biggest waste is everyone discovering the same things alone.
🚫Don't ignore quality because it was fast. AI can make it easy to miss problems at scale.
